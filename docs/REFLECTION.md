# Sentinel — REFLECTION.md（反思报告）

> 本报告由作者本人撰写，总结本项目在 AI 协作方法论上的实践观察与批判性
> 思考。全文约 2200 字。

---

## 1. 哪些 Superpowers 技能发挥了最大作用

**最大作用：`writing-plans`。** 它把"治理做深"的宏大想法拆成了 16+11 个
2–5 分钟、每步带失败测试和文件路径的 task。没有它，subagent 就没有可
执行的"合同"。其次是 `test-driven-development`——它把"确定性"从一句口号
变成每 5 分钟一次的客观校验，尤其是治理机制（guardrail、HITL 状态机、
audit）这类"一旦出错会静默放行危险动作"的代码。

**形式大于实质的部分：`using-git-worktrees` 的两阶段评审流程在 Phase 1 表现
有限。** Phase 1 我以内联方式推进（直接提交 main），worktree/PR 纪律到
Phase 2.5 才真正发挥作用。部分技能（如 `finishing-a-development-branch`）
的仪式感强于实际收益——对单人项目，merge 决策其实一直很明确。

## 2. TDD 在 AI 协作下是阻碍还是放大器

**是放大器，前提是"红"必须是真的红。** 本项目最有价值的一次 TDD 时刻不是
"测试通过了"，而是冷启动的第二个 agent 在 `RiskLevel` 上写出
`LOW < HIGH` 这样残缺的断言，测试"通过了"却未覆盖 `__le__`/`__ge__`——
我在评审时补全了它。这证明 TDD 的纪律不只是"先写测试"，更是"测试要能
抓住真实的错误"。

TDD 在 AI 协作下的独特价值：**它让 subagent 的"完成"有了客观定义。**
subagent 无法被说服，但可以被 pytest 说服。当 agent 报告"done"时，我不
用信任它，只需运行测试。反过来，TDD 也保护我——治理代码里任何一次
"先实现后补测试"，都意味着护栏逻辑退化为不可验证的提示词。

## 3. subagent 能自主运行多久而不偏离

**以 task 为边界：单个 task（约 20–60 分钟）内可以完全自主；跨 task 会
偏离。** Phase 2.5 的 4 个 task 由 4 个新鲜 subagent 各自完成，每个都精确
落点在自己的 brief 上，无一定出轨。但观察冷启动试运行：当让一个 agent 连
续推进"主循环 + 机制演示"两个相邻 task 时，它在第二个 task 里开始自行
发挥（例如想在 `max_turns` 到达时抛异常）。**结论：task 越小、边界越
显式，自主越可靠。**"自主运行 2 小时不偏题"需要把 2 小时切成 4 个有独立
验收的 30 分钟片段。

## 4. 最优 task 颗粒度

**能在一次会话内完成、且有一个客观验收（通常是测试）的最小单元。** 我的
体感是"一个 task = 一个文件模块 + 它的失败测试 + 一次提交"。例如 Task 2
"LLM 抽象 + MockLLM"是 20 分钟，Task 13 "主循环"是 40 分钟——后者略偏大，
导致需要补一次修复 commit。小于 10 分钟的 task 反而增加调度开销。

## 5. SPEC/PLAN 质量如何影响实现质量：一个具体案例

**"规约不清导致 subagent 偏离"的案例是 `FeedbackReceived` 事件。** SPEC
Phase 1 初稿只写"yield `FeedbackReceived`"，没有定义 payload 结构。冷启动
的第二个 agent 据此做了两种不同解读（`failures` 放对象列表还是字符串列表），
并暂停询问。这不只是"实现变慢"，而是**歧义被传递到了运行时协议**——前端
和 audit 都要消费这个事件，一旦结构错误，就要改联动。我随后在 SPEC 中补
上 `{"passed": bool|None, "failures": [str, ...]}` 的精确形状，实现才收敛。

**教训：SPEC 里每一个"输出/事件/返回值"都必须定义到字段级，尤其是 agent
之间、agent 与 UI 之间共享的协议。**

## 6. 最有效的 prompt / context 策略

**把"约束"放进结构，而不是放进提示词。** 本项目最重要的 context 设计不是
某句 prompt，而是：
1. **PLAN 的 task 直接给出完整失败测试代码**，subagent 不需要"理解意图"，
   只需要"让测试变绿"；
2. **可注入 collaborator（LLMProvider / ApprovalPolicy / SandboxBackend /
   keyring backend）**——这让测试环境与生产环境共享同一份核心代码，mock 的
   注入点就是约束的声明处；
3. **YAML 配置里声明 guardrail 模式、工具白名单、审批超时**，而非要求 LLM
   "注意安全"。

为什么有效：因为这三者都是**代码级/数据级约束**，LLM 的遵从概率不再是变量；
它们可以被单测锁定。提示词只能建议，结构才能保证。

## 7. 凭据与分发要求，迫使我想清了什么

**凭据。** 若无这门课的强制要求，我很可能把 API key 直接塞进 `sentinel.yaml`
或环境变量。要求迫使我做了两件事：威胁模型（§4.2 那张表）和**"状态查询不
回显明文"**。后者让我意识到：即便用 keyring，只要 `status` 命令把 key 打
到 stdout，就可能在 CI 日志/终端历史里泄露。这一条直接塑造了 CLI 的行为。

**分发。** 若没有要求，我不会思考"在一台全新机器上怎么跑起来"。它迫使我把
"InProcessSandbox（无 Docker）→ Docker 沙箱"的降级路径、`docker run -e
OPENAI_API_KEY=...` 与 keyring 的取舍、以及"容器里挂 docker.sock 造沙箱"的
安全面（SPEC R1）都写清楚。这些正是 harness 项目"工程深度"的所在。

## 8. 如果重做，我会改变什么

1. **Phase 1 也走 worktree/PR 流程**，而不是内联提交 main。虽然结果一样，
   但过程证据（每个模块一个 PR、评审记录）会更完整，也符合课程对"完整
   commit 历史与 PR 工作流"的期待。
2. **冷启动验证提前到"写完 PLAN 立刻做"**，而不是放在两个 task 上。
   早做能让 SPEC 缺口在写第一行代码前就暴露。
3. **对 subagent 的输出做更早的代码级抽查**，而不只是跑测试。Phase 2.5
   最终评审才发现的 XSS（`innerHTML`）与竞态，本可以在第一个 task 的
   spec 合规评审时就抓到。

## 9. 对 Superpowers 方法论的批判

**它假设工程师会诚实地运行工具、会真正阅读 agent 的输出。** 这个假设在我
的项目里基本成立，但有两个破绽：

1. **它防不了"自欺性绿灯"。** 如果实现者（人）和 agent 一样只关心测试变绿，
   就会写出 `LOW < HIGH` 这类空转断言。方法论给了流程，却没给"测试本身
   是否有效"的校验——这是它最大的盲区，只能靠人的判断补上。
2. **它对"内容物 vs 机制"的边界高度敏感（§A.4 是好事），但对"内容物里也
   有工程"不够宽容。** 例如我的 `sentinel.yaml` 与前端 HTML 是不计入
   harness 实现量的，但配置 schema 的设计（哪些字段必填、如何 fail-fast）
   和前端的事件协议其实也是工程。它把"判断力"的责任全部推给了人——这
   正是课程想教的：**流程守住了纪律，但"做什么、做对了吗"永远无法外包。**

## 结语

这门课最真实的收获是：当 LLM 能完成大部分编码时，我的价值不在于写得更快，
而在于**知道该往哪个方向深挖（治理）、用什么客观信号判定正确（TDD/mock）、
以及为共享协议（事件结构、凭据流、分发路径）定下不可妥协的边界**。
Superpowers 给了我流程脚手架，而脚手架之上的一切判断，都只能由我完成。
